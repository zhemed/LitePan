# defer-unstable-file-upload-guard（决策记录，不实施）

## Goal

**决策记录**：对"上传途中文件被修改"导致的失败（`HTTP: ContentLength=X with Body length=Y`）的修复方案，经用户决定**暂不实施，直接归档备查**。

## 已查明的根因（2026-09-10 定位，代码级）

- 计划阶段 `uploadutil.StatLocalFile` 用 `os.Stat` 记录文件大小
- 驱动按该大小声明 `Content-Length`；**115 单分片路径**（`drivers/115_Open/upload.go:1007-1023`）直接包住文件句柄，**没有 `io.LimitReader`**
- 文件在上传途中增长（典型：SQLite 的 `-wal` 边写边传）→ 实际发送字节 > 声明 → Go transport 中断请求
- 对照：115 分片路径（同文件 1121 行）与 189 驱动均用 `io.LimitReader` 按计划大小截断 → 不会触发

## 备选方案（四层，按代价排序，均未实施）

| 层 | 做法 | 代价 |
|---|---|---|
| A 长度恒定 | 115 单分片补 `io.LimitReader`；抽公共封装防超发 | ~30 行 + 单测，风险极低 |
| B 一致性校验 | 上传前后比对 size/mtime/inode，不一致则给出明确原因（"文件在上传过程中被修改"）+ 前端归类 | ~半天 |
| C 默认排除 | 排除规则默认含 `*.db-wal`/`*.db-shm`/`*.db-journal`，可配置 | ~半天 |
| D 一致性快照 | SQLite `VACUUM INTO` / 源侧文件系统快照，备份才可真恢复 | 1–3 天，需设计 |

**关键判断**：即便修好传输（A/B），把活的 WAL 传上去也不是有效备份；"备份 SQLite 目录"场景的真正解法是 C + D。

## 未来触发条件（满足其一再开任务）

1. 再次出现同类失败且影响使用（例如其他追加型文件上传失败）
2. 用户需要"可恢复的数据库目录备份"能力（→ 直接做 C + D）
3. 上游/其他驱动出现同源问题需要统一防御
