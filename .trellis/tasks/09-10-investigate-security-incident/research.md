# 事故调查报告（修订版）：我的维护引入的严重缺陷

> 前一版把事件误判为"凭据泄露"（**该问题客观存在，但非用户所指**）。本版为用户所指方向：**维护工作（0.0.23~0.0.28）引入的严重缺陷**。以下缺陷均已**定位到代码 + 复现**。

## A. 【高危·可致云端数据丢失】保留策略削弱"批次根目录删除"保护（0.0.28 引入）

**机制**
1. 我在 0.0.28 加了保留策略：自动清理历史成功记录（`internal/upload/retention.go`）
2. 前端"删除任务（含云端文件 + 批次根目录）"的安全前提是 `BatchDelete` 的完整性校验：**该批次在内存中的所有任务都必须被选中**（`internal/upload/delete.go:86-103`）
3. 保留策略清掉部分记录后，内存里该批次只剩少数几条 → 用户**只选中看得见的几条**，校验却判定"整批已选" → **删除云端批次根目录（连同目录内全部文件）**

**复现（单元测试，已固化）**：`internal/upload/retention_guard_test.go`
```
3 条同批次记录 → 保留策略清理 1 条 → 用户选中剩余 2 条执行删除
→ 实测：云端批次根目录被删除（[[batch-root-id]]）
```
**影响**：用户以为只删了几条记录，实际可能删掉云端整个文件夹。**这是本次维护引入的最严重缺陷。**

## B. 【中危】删除接口接受空 file_id 并报成功（长期存在，本次排查发现）

```
DELETE /api/files/delete  {"file_ids":[""],"parent_id":""}
→ {"success":true,"message":"已删除到回收站 1 个项目"}   ← 实际什么都没删
```
**影响**：用户以为删掉了，云端文件仍在（"删除无效"体感）。

## C. 【中危·显示错误】徽标/导航计数把 paused/failed 计入"进行中"（0.0.27 引入）

`web/src/composables/upload/useUploadTaskStore.ts:124`
```ts
const active = server.total - counts.success - counts.skipped;  // 把 paused/failed/canceled 全算成"上传中"
```
**影响**：有暂停/失败任务时，徽标显示"上传中 N"（实际是暂停），误导用户。

## D. 【流程问题·已自查】我在真实云盘做过端到端测试且未立即清理

排查期间我在用户云端 root 建过 `f1/f2/f3.bin`、`nested_probe.bin`、`sec_probe_del`、`sec_root_test`、`probe2/`、`e2e_probe.bin` 等测试物，**现已全部清理**（root 已恢复为最初的 9 项）。教训：真实账号的端到端测试必须"用完即清"，优先用单元测试复现。

## 修复设计（建议，待批准）

| 缺陷 | 修复 | 要点 |
|---|---|---|
| A | ①保留策略**跳过 owned 批次根任务**（`result.batch_root_owned==true` 且 `batch_root_id!=""`）；②`BatchDelete` 增加**持久化完整性判据**：批次创建时写入 `batch_task_total`，删除根时要求"选中数 == 该批历史总数"，缺失时保守拒绝根删除；③保留策略清理后**同步收缩**该批次的可删性（即使 ①② 失效也不误删） | 三重保护，任一失效不致命 |
| B | API + 服务层过滤空/空白 file_id；全为空返回 400 VALIDATION | 与既有参数校验一致 |
| C | 计数改为明确状态桶：`active=pending+running`、`paused=paused`、`failed=failed+canceled`、`done=success+skipped` | 前端 15 行内改动 |
