# 调查报告：还能优化什么（2026-09-10，7814 任务规模实测）

## 一、实测数据

| 指标 | 数值 | 评价 |
|---|---|---|
| 列表 API 服务端耗时 | **95ms**（7814 条全量序列化） | 后端不是瓶颈 ✅ |
| 列表 API 响应体 | **5.41 MB** | 传输 + 前端解析/响应式的主要成本 ⚠️ |
| SSE 订阅首帧 | **5.41 MB 全量快照**（`kind:"snapshot"`） | 每次打开面板/重连都要传一遍 ⚠️ |
| DB 索引 | account/status/batch_id 三索引齐备，查询走索引 | ✅ 无需动 |
| 字段占比（2.88MB 可归因部分） | `result` 23.3%、`cleanup_local_path` 14.3%、`message` 8.6%、`target_display_path` 8.2%、timestamps 9.4% | 前两项可瘦身 |

## 二、可优化项（按性价比排序）

### 1. 载荷瘦身（后端，低风险，收益 ~11%）
- **砍 `cleanup_local_path`**（412KB）：纯服务端字段，前端 0 引用 ✅ 无风险
- **瘦 `result`**（673KB）：`file_name`/`size` 与顶层字段重复，只保留 `file_id`/`parent_id`/`batch_root_*` → 省 ~200KB
- 合计 5.41MB → **~4.8MB**

### 2. 列表分页/过滤/汇总（后端+前端适配，中等改动，收益最大）
- API 加 `?status=&batch_id=&limit=&offset=`，响应带 **`counts`（各状态计数）+ `batches` 聚合**
- 前端：徽标/分类计数改用 `counts`；当前分类只拉窗口（如 500 条）；批次树用 `batches` 聚合
- 效果：面板打开 **5.41MB → ~0.3-0.6MB**；响应式对象 7814 → ~500（主线程工作量约 10-15×↓）
- SSE 快照同样瘦身（或改为 counts + 窗口）

### 3. 前端计算热路径（中等改动，收益大，与规模成正比）
- `uploadTaskBadgeText`：**4 次全量 filter**（failed/paused/success/总数）→ 改为单次遍历（7814 → 1 遍）
- 批量暂停：对 N 个任务**逐个响应式 patch**（与刚才卡死的 resume 同类）→ 改为单次批量请求后一次刷新（resume 已改，pause 未改）
- 批次树 `buildUploadTaskLevel(uploadTasks)`：每次 delta 全量分组 7814 条 → 可按 batch_id 记忆化/只重建受影响批次
- `displayUploadTasks`/`activeUploadTasks`/`selectedRows` 等 computed 链在每次 delta 全量重算 → 若采用第 2 项（工作集变小）自动缓解

### 4. 工作集治理（运维/策略，改动小）
- 历史任务（如 5800+ 成功记录）长期留在列表 → 可加**保留策略**：默认视图只保留近 N 天/最近批次，历史归档查询
- 效果：把默认工作集从 7814 压到几百，是所有前端问题的根治手段之一

## 三、不建议动的

- **上传吞吐**：并发的 1 + 500ms 门是用户设定；实测 60/分钟已接近设计上限（1MB 文件 ≈1s/个 + 门），不再优化
- **后端序列化**：95ms 无优化价值
- **DB**：索引齐备

## 四、建议实施顺序

1. **第 3 项的前半（徽标单遍计数 + 批量暂停去 N-patch）**：半天级、纯前端、立竿见影
2. **第 1 项（载荷瘦身）**：小时级、后端为主、零风险
3. **第 2 项（分页/汇总）**：1-2 天、跨前后端、根治
4. 第 4 项按需（取决于你希望保留多少历史）
