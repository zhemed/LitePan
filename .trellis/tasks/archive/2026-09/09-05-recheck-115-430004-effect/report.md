# 430004映射实际作用重查报告

重查时间：2026-09-05 · 只读 · 针对"上次没讲清实际作用"的返工

## 实际作用（一句话）

**把"云端东西没了"从"整单报错"降级为"跳过这一件、其他照做"。** 这 2 行是传感器，是否产生用户可感知的行为，取决于下游有没有执行器。

## 用户故事（具体到操作与提示语）

### 故事 A：作者线上真实踩坑（STRM 扫描，上游实证，本地不适用）

- 操作：115 STRM 增强扫描（全量清单里记着一批目录 ID）。
- 撞上：其中某目录在云端已被删 → `ResolveDirPath` 调 115 接口返回 430004。
- 无映射：430004 进 default 变成通用 `DRIVER_ERROR` → `isNotFoundError=false` → **整个扫描任务失败**，用户看到"扫描失败"，连正常的目录也不扫了。
- 有映射：`CodeNotFound` → `isNotFoundError=true` → 该目录记 `"115 返回目录不存在，已跳过关联的 N 个文件（示例：a、b、c）"`，且因"有目录无法解析"**停止本次本地清理防误删**，其余目录照常扫描完成。
- 本地：STRM 模块已删，此故事不适用——但它是最强证据，证明 **430004 实义=目标不存在**（作者线上验证过的，不是拍脑袋）。

### 故事 B：删除幂等（本地适用，唯一现存执行器）

- 操作：用户在 LitePan 面板多选删除，其中一件已在别处（手机端/网页端）删过；或彻底删除时文件已在回收站外消失；或批量删重试。
- 撞上：`DeleteFiles→trashFiles→apiCall` 对那件返回 430004。
- 无映射（现状）：整单报"删除失败"（502 `115 API 错误(430004)`）——即使用户要删的东西本来就已经没了，还吓用户一跳；彻底删除还会再空轮询。
- 有映射：`file/service.go:229` 命中 `CodeNotFound` → 日志"删除文件时文件已不存在，视为成功"，其余文件照常删，用户看到"删除成功"。

### 故事 C：列取提示语（本地适用，纯体验）

- 操作：点进一个云端刚被删的目录。
- 现状：502"115 API 错误(430004)"；合入后：404"文件不存在"。只差一句话。

## 430004 实义来源

- 最强来源：上游作者线上用法（映射命名 + `"115 返回目录不存在"` 日志 + 配套 130 行跳过逻辑），属运行实证。
- 公开渠道：4 路并行搜索（中英错码表/社区/文档），无 115 官方错码表命中，AI 问答互相矛盾（一个说认证失效、一个说文件不存在）。
- **结论：官文定义未能独立验证**，采信作者实证；残留不确定性：若 115 把 430004 复用于"回收站内/无权限/敏感内容"等非"不存在"场景，则故事 B 会变成"假成功"（以为删掉实际还在）。无证据表明如此，但无 115 账号也证伪不了。

## 合并的理由

1. 真实坑非臆测：故事 A 是作者线上 decid 的修复（`fix115strm`），传感器+执行器配套，码义有运行背书。
2. 故事 B 是通用刚需：多选删除/重试/双端操作必撞"已删又删"，现在报失败是误报；且 189/LocalFs 早已产出 `CodeNotFound`，115 是唯一掉队的驱动，合入即三驱动语义对齐，下游"视为成功"一视同仁。
3. 风险面≈0：单码收敛（仅 `==430004`），与 401 系/406 前缀无重叠，不进认证误判；`apply --check` 通过；与 0.0.14 认证链正交。
4. 账好算：2 行，现在不合，以后每次读 115 transport 都要重想一遍；合了 upstream diff -1。

## 不合并的理由

1. 零验证：无 115 账号，合入后该分支永久零覆盖；若残留不确定性成真（430004 另有他用），删除"假成功"比"误删报"更伤信任——错报吓人，假成功误人。
2. 本地收益只剩一路：最大执行器（STRM 跳过+防误删）已删，故事 A 的 130 行价值本地享受不到；为故事 B 的提示语+幂等合 2 行，性价比见仁见智。
3. 无需求方（YAGNI）：全库唯一账号是天翼，115 代码现在跑都不跑；为用不上的驱动改代码，违反"不提前付账"。
4. 无窗口压力：2 行补丁随时可合，等哪天绑了 115 账号、真机验证一把再合，效果相同且零赌注。
