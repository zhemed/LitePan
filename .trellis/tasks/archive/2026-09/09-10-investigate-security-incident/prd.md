# investigate-security-incident

## Goal

调查「重大安全事故」。用户未说明具体事件，因此本任务分两步：**① 立即开展全面安全排查**（主动发现是否存在真实事件与影响面）；**② 结合用户线索定位并处置**。

> 安全事件优先：若排查发现高危项（凭证公开泄露、未授权访问等），先给结论与紧急处置建议，必要时请求授权立即止血。

## Requirements

1. **凭证与密钥暴露面**
   - 仓库（含 git 历史）中是否存在明文口令、Token、`secret.key`、`.env`、备份文件
   - 已推送远端（GitHub / ghcr.io）仓库的可见性，以及公开可见内容中是否含凭据
2. **认证与访问**
   - 登录/鉴权日志：失败尝试、来源 IP、异常时段、管理员会话
   - 服务暴露面：监听地址、对外可达性、是否需要认证、是否存在匿名访问路径
3. **数据与凭据存储**
   - 数据库敏感字段（账号 Token/Cookie/sessionKey）、文件权限、备份文件权限
   - 容器与宿主：特权模式、挂载、`pid host`、`/dev/fuse` 的暴露含义
4. **日志与错误信息**
   - 应用日志/任务错误字段是否携带敏感值（如 189 `sessionKey`），可见范围
5. **影响评估与处置方案**
   - 事件分级（是否真实发生、影响范围、是否需紧急轮换凭据）
   - 处置清单：止血（轮换/下线/限制）→ 修复（代码/配置）→ 复盘（规范）

## Constraints

- 只读排查为主；任何凭据轮换、权限变更、仓库可见性变更等处置动作，须先给方案并经用户确认（项目规则：改密必须 ask_user_question）。
- 不臆断事件性质；无法证实的一律标注"未证实"。

## Acceptance Criteria

- [x] 排查完成：凭证暴露面/认证访问/数据存储/日志/网络暴露/容器特权 六面取证（前一版报告）
- [x] 重新定性：用户所指为**维护引入的严重缺陷**，已定位 3 个（A 高危数据销毁、B 中危校验漏洞、C 中危计数错误）
- [x] 影响面：A 可致云端文件夹被误删（单元测试复现）；B 删除无效；C 显示误导
- [x] 处置建议：A 三重保护修复（优先）；B 参数校验；C 计数分桶；另附 D 自查（我的云端测试残留已清净）
- [x] 已两次核对（用户回复：我的维护引入严重 bug，未描述具体现象）→ 以独立复现为准
- [x] 门禁 + 归档 + journal + push
