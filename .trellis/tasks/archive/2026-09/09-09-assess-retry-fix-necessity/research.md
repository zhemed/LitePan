## 逐项评估

### 1. HTTP 5xx/429 重试放行（init/commit 路径）——建议：修 ✅

- **收益（实测支撑）**：本批次 14 次失败全部是单发瞬时错误（同窗口后续 1900+ 文件全成功——即每次 511 之后 189 立即恢复），2-3 次重试几乎必成功。当前 0.7% 残留全部要手动重传；更大批次线性放大（5000 批 ≈ 70 个）。修后趋近 0。
- **成本**：~30 行——`rawJSON/rawForm`（transport.go:228/264 两个错误构造点）把状态码带进错误（`WithDetails` 或轻量类型），`retryableUploadURLFailure` 增加识别（3 个调用点全走既有重试循环与 `retryDelay` 退避，无需新机制）。
- **风险**：低——重试上限既有（3 次）、退避既有（递增 300ms×n）；429 场景有 500ms 门兜底，本批次实测 429 = 0 次；不放大请求总量（仅失败路径重试）。
- **分叉代价**：~30 行独立函数级改动，上游若日后改此函数也易合并。
- **不修的代价**：每批次 ~0.7% 手动重传残留；189 抖动加长时残留更高（尾段 3 连发已现苗头）。

### 2. 认证加载取消的 WARN 噪音——建议：不修（可顺带）⚪

21:37:32 单时刻 10 条，全部来自被取消请求的认证状态加载（取消是正常行为）。无业务影响。若日后改 transport/driver 日志时顺带加一行 `if ctx.Err() != nil { return nil }` 降噪即可，不值得单开任务。

### 3. 大批量任务树虚拟滚动——建议：不修 ❌

2000 节点批次全程（含 delta 事件流）无卡顿投诉，0.0.18 时代的顾虑已被定向广播化解。无实证痛点不做。

### 4. 测试数据清理（云盘 1986 个 + 本地 2G）——运维操作，非代码 ⚪

需要时一句话执行；本地目录在 mounts 下容器可见，云盘侧删除走 UI 或 API 批删。

## 总建议

**只修第 1 项**：半小时级改动 + 2 组单测（511→重试成功 / 会话失效→不重试防误重试），随下个版本（0.0.20）发布。其余不修。
