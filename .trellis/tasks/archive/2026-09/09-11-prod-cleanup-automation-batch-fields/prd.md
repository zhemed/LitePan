# 09-11-prod-cleanup-automation-batch-fields

## Goal

用户授权（2026-09-11，选项「等这批传完后清掉，恢复平铺」）：待生产机 `10.0.0.11` 当前那批自动化上传任务**全部结束后**，清除其 `batch_id/batch_name`（`auto-%` 前缀），使任务面板恢复**逐文件平铺**显示。

## Background

- 0.0.35 为自动化运行写入批次身份 → 面板把该批 819 个文件折叠成一行「定时任务 定时全局备份（传输中 13/819）」。
- 0.0.36 已回退该写入（后续运行不再带批次 id），但**存量 819 条任务数据库里仍带**，故当前那一行仍会折叠。
- 用户选择在批次结束后清理存量数据（本次为**生产数据修改**，需按授权范围严格限定）。

## Requirements

- **R1 触发时机**：仅在该批任务无 `pending/running` 之后执行（用户确认批次结束，或只读查询确认到位）。
- **R2 备份先行**：修改前对 `data/litepan.db` 做一次一致性备份（`sqlite3 .backup` 或等价只读复制），落盘路径写进记录。
- **R3 最小写入**：仅执行
  ```sql
  UPDATE upload_tasks SET batch_id='', batch_name='' WHERE batch_id LIKE 'auto-%';
  ```
  不得触碰其它列/其它任务（先 `SELECT count(*)` 与受影响行数比对）。
- **R4 前后对比**：记录修改前后 `select status,count(*)`、`batch_id` 非空计数、受影响行数；面板行为由用户确认（平铺）。
- **R5 风险评估留档**：`research.md` §5 已记录两处读取方（熔断分组键 → 退化为 `acct|target` 仍受保护；批次根删除守卫 → 该批次「批次根」语义退化），执行记录中重申。
- **R6 只做这一件事**：不升级镜像、不改配置、不动上传队列；如需升级由用户另行操作。

## Constraints

- 生产机操作须**只读优先**、写入最小化；口令不落盘。
- 若批次尚未结束（仍在上传），**不得提前清理**（避免影响熔断/删除守卫语义）。

## Acceptance Criteria

- [x] 执行前已确认无 `pending/running` 任务
      → `success 819 / failed 0 / paused 0 / pending 0 / running 0`（见 research.md §1）
- [x] DB 备份：**未执行**（无写入对象；`auto-%` 行为 0 ⇒ 无行可改，按最小写入原则不做无对象写入与备份）
- [x] `UPDATE`：**未执行**——前置 `SELECT count(*) WHERE batch_id LIKE 'auto-%'` = 0，目标状态已达成
- [x] 复核：`batch_id` 非空 = 0、`batch_name` 非空 = 0、`auto-%` = 0；状态计数 `success 819` 无异常
- [x] 用户已确认升级后**验证成功、传输完毕**；无批次字段 ⇒ 面板无折叠（由版本行为自然达成）
- [x] 全程零写入（仅 `docker inspect` + `mode=ro` 查询）；风险评估与前后数据见 research.md

## Notes

- **验收措辞校准（证据驱动）**：本任务以「目标已达成、无需写入」闭环——用户升级到 ≥0.0.36 后的新运行不再写批次身份，且 0.0.35 存量批次已不在库中（`auto-%` = 0）。因此备份/UPDATE 两项由「执行」变更为「因无对象而跳过」，并在 research.md 中给出前置查询证据。

- 本任务**等待外部条件**（批次结束）：先完成规划，待用户告知「这批传完了」或我方可只读确认后，再 `task.py start` 并执行。
- 执行时遵循「PRD → 门禁 → start → 实施 → check → archive」顺序。
