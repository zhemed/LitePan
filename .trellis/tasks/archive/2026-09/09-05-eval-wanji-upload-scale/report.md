# 万级（1〜2万文件）上传链路评估与建议

评估时间：2026-09-05 · 前提：走**从服务器上传**面板（A-road 已验证链路）；浏览器拖拽入口另议（见 §5）

## 结论

**B-road 不够，但 B1+B2+B3 是必要基础；之外再加 1 处 5 行加固 + 并发调优 + 阶梯实测即可，不需要重构。**

## 分段瓶颈（按致命度）

1. **致命·前端全行渲染**：`TaskPanel` 无虚拟化（`visibleRows` 只是搜索过滤），2 万行全量 v-for；且每 400ms 全量 `listTasks` 替换触发全表重算 + 重渲染。→ B3 批量折叠解决（上游自带 1 万任务聚合 <1s 实测脚本为证）；单目录 2 万平铺是残留极端（B-road不管，发生再加虚拟列表）。
2. **严重·全量轮询+S全量快照**：400ms 拉全量（2 万行约 10MB JSON ×2.5次/s）；后端每进度 tick 全量 SSE 快照。→ B1（增量 dirty-ID）+ B3（stream 替代轮询）解决；面板初始一次全量可接受。
3. **严重·浏览器进度风暴（拖拽流）**：`updateLocalUploadTask` 每次同步 `JSON.stringify+setItem` 全量（O(n)），XHR 每 tick 触发 → 2 万行下每 tick 百 ms 级卡顿。服务器面板流不受影响（local 任务≈0）。
4. **中等·服务端逐文件成本**：整文件 MD5（秒传必需，本地盘可接受）+ 每文件数个 189 API；并发上限 5（默认 3）；建目录 List 按目录缓存（已优化）；DB 仅 transition 期 persist（progress 不落库，好）。2 万文件/并发5/平均1.5s ≈ 100 分钟量级，429 由 0.0.14 熔断接住（不误判 fatal）。
5. **轻·sessionStorage 配额**：序列化约 300B/行，2 万行约 6MB > 5MB 配额，`flush` 无 try/catch 会抛（仅影响会话恢复，不影响上传）。→ 5 行加固必做。
6. **无分页**：`listUploadTasks` 全量（初始一次可接受）；DB `Upsert` 按 100 分批，SQLite 无压力。

## 建议（分级）

- **必做**：B1（独立先合，向后兼容）→ B2+B3（含 TaskPanel 手工移植 + 真机千级 UI 实测）；sessionStorage `setItem` 加 try/catch（可并入 B1 任务，5 行）。
- **调优**：任务并发调至 5，观察 189 的 429 率后再定（熔断已兜底）。
- **验证**：`fallocate` 造 1k→5k→10k→20k 阶梯，监控面板帧率/接口耗时/DB/429 率；先 1k 验 B 全功能。
- **不做**：浏览器拖拽走万级（20k POST 穿浏览器，需架构重做；若你真实入口是这个，告诉我另立项）；虚拟列表暂缓（等单目录平铺真卡再说）。
