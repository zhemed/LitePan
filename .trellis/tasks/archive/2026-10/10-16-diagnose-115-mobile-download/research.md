# 排查记录：115 直链手机端打不开（net::ERR_INVALID_RESPONSE）

**结论先行**：这条链接**不是"手机端坏了"，而是"签名只对生成它的那个网络（IP）有效"**。
手机（蜂窝网络/别的 Wi-Fi）请求时源 IP 不同 → CDN 判定签名无效 → 返回 **403 + 85 字节错误体**，
而这个错误体带着 `Content-Type: application/zip` + `Content-Disposition: attachment`，
移动端浏览器/WebView 处理这种"附件 + 非 2xx"响应时就报 `net::ERR_INVALID_RESPONSE`。

---

## §1 实测证据（本机对用户提供的那条直链做最小请求）

| 请求 | 结果 |
|---|---|
| 桌面 Chrome UA（HEAD） | `HTTP/1.1 403 Forbidden`，`Server: AliyunOSS`，`Content-Type: application/zip`，`Content-Length: 85`，`Content-Disposition: attachment` |
| 安卓 Chrome UA（HEAD） | **与桌面完全一致**（同样 403/85 字节） |
| 带 `Referer: https://115.com/` | 403 `invalid signature` |
| 115 浏览器 UA | 403 `invalid signature` |
| 不带 UA | 403 `invalid signature` |
| `Range: bytes=0-0` | 403 `invalid signature` |

响应体（85 字节，原样，request_id 隐去）：

```json
{"status":403,"message":"invalid signature","request_id":"…"}
```

**推论**：签名校验与 UA / Referer / 请求方式（HEAD/GET/Range）**都无关**，只与"谁在请求"有关；
本机（不同公网 IP）无论如何都拿不到文件 → 与用户"电脑能下、手机不能"的差异**只能用源 IP 解释**。

**链接时效**：`t=1792146341` 解码为 **2026-10-16 18:25:41（北京时间）**，实测时还有约 28 分钟才过期
→ **不是过期问题**（过期会是另一类错误）。

## §2 为什么两端表现不同（行为差异的机制）

CDN 的 403 响应头里同时带着 `Content-Type: application/zip` 与 `Content-Disposition: attachment`：

- **桌面 Chrome**：把"附件"响应直接交给下载器 → 用户看到"能下载"。**需要核对**：
  桌面上那个文件到底多大？若只有几十字节/几百字节（或不是有效 zip），说明桌面拿到的也只是这个错误 JSON，
  只是被浏览器存成了文件（用户误以为成功）。
- **移动 Chrome / 应用内 WebView（微信、QQ、夸克等）**：对"非 2xx + 附件"的顶层导航往往直接失败，
  报 `net::ERR_INVALID_RESPONSE`（部分 WebView 另会显示"网页无法打开/无法下载"）。

## §3 判定

| 候选原因 | 判定 | 依据 |
|---|---|---|
| 链接已过期 | ✗ 排除 | `t=` 还有 28 分钟 |
| 按 UA 分流（手机 UA 被拒） | ✗ 排除 | 桌面/移动 UA 响应逐字节相同 |
| 需要 Referer/Cookie | ✗ 排除 | 带 115 Referer 仍 `invalid signature` |
| **签名绑定请求方 IP（热点保护）** | ✓ **最可能** | 同一链接在不同 IP 上恒定签名失败；同网络（电脑所在网络）成功 |
| LitePan 的重定向/代理 bug | ✗ 不成立（本链路） | 用户是直接打开 CDN 直链，没经过 LitePan；且 302 直读本身不改签名 |
| 移动端 WebView 不支持附件下载 | ✓ **放大器** | 它决定了"403 在手机上表现为错误页而不是小文件" |

## §4 让用户确认根因的两个对照实验（各 1 分钟）

1. **手机连上与电脑同一个 Wi-Fi**（关掉蜂窝数据）再点这条链接：
   - 能下 → **IP 绑定确认**（结论成立）；
   - 仍不能 → 再看手机是否用了代理/VPN（企业 VPN、加速器都会换源 IP）。
2. **核对桌面上那个"下载成功"的文件大小**：真实文件应为 `s=52428800` 对应的分片大小量级（约 50 MB，
   完整文件另按 `us=`/`uc=` 计算）。若只有几十/几百字节 → 桌面其实也没成功，只是把 403 的 JSON 存成了文件。

## §5 绕行办法（手机端立刻可用）

1. **走 LitePan 代理下载**：LitePan 的下载接口支持 `force_proxy=1`（`internal/api/files.go:78`），
   由服务器（在"绑定网络"里）去取文件再转发给手机 —— 手机端 IP 不再参与签名校验。
2. 用 **115 官方 App** 打开/离线下发（App 内部会重新取一条属于自己的直链）。
3. 在**同一 Wi-Fi** 下用手机浏览器打开（若 §4.1 验证为 IP 绑定，这条必通）。
4. 手机端避免用微信/QQ 内置浏览器，改用系统浏览器 + 下载管理器。

## §6 产品级建议（LitePan 侧，未实施，待用户定）

- 115 直链是**短时 + 绑定请求方 IP** 的：`drivers/115_Open` 取链后，客户端若来自不同网络（手机流量），
  302 直读必然失败。可考虑：
  1. 对 115 账号把**默认下载模式设为代理**（或在检测到直读失败时自动回退代理）；
  2. 在移动端 UA 或跨网请求时**自动加 `force_proxy`**；
  3. 直读失败（403 invalid signature）时，前端给出一句明确提示 + 一键切代理（现在只会表现为浏览器错误页）。
- 本轮**只排查不改代码**；若要做，另开任务（涉及下载/播放路径与前端提示）。
