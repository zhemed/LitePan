# 回答：其它软件（Alist、Emby…）会不会踩同一个坑

**判据（唯一）**：看**取链方**与**下载方**是不是同一个身份（UA/客户端）。
同一 → 无事；不同 → 115 必回 `403 invalid signature`，若该 403 带 `attachment` 头，手机端就显示
`ERR_INVALID_RESPONSE`（本次就是这么被看到的）。

## 逐类速答

| 工具/场景 | 取链方 → 下载方 | 会不会踩 |
|---|---|---|
| **115 官方 App / 网页** | 115 自己 → 115 自己 | 不会 |
| **Alist（本体）直链模式** | Alist 服务端（Alist 的 UA/凭据）→ 手机浏览器或系统下载器 | **会** —— 与 LitePan 之前完全同型：签名在 Alist 取链那一刻就绑死在 Alist 的 UA 上 |
| **Alist 代理/中转模式** | Alist 服务端 → Alist 服务端（手机只连 Alist） | 不会 |
| **Emby / Jellyfin 常规部署** | Emby 服务端 → 手机播放器（连的是 Emby 自家端点，不碰 115） | 不会 |
| **Emby/Jellyfin + STRM/直链指向 115 CDN** | 某个服务端 → 手机直接取 115 直链 | **会**（同型问题） |
| **别的网盘挂载软件（WebDAV 客户端、播放器直链）** | 视实现：直链→会；自带中转→不会 | 用上面判据判断 |

## 手机侧还有一个变量：谁在下载

同一台手机、同一个 App 也可能时好时坏，因为"下载"这一步常常不是浏览器干的：
安卓浏览器会把附件交给**系统下载组件**（UA 与浏览器不同），微信/QQ 内置浏览器、夸克、迅雷等各有自己的 UA。
所以判据要落到**真正发起 HTTP 请求的那个组件**上，而不是"我用的是哪个 App 打开的"。

## 已知解法（两种，二选一）

1. **让下载方用自己的身份重新取链**：就是我给 LitePan 做的两跳握手（先空附件 → 下载组件带自己的 UA 回来 →
   按它的 UA 取链 302）。工具若不改代码，一般用不了这招。
2. **让中间的服务器代下**：即"代理/中转"。Alist 侧的对应做法是把该存储设成**代理下载**（不要让客户端直连
   上游 CDN）；LitePan 侧是 `force_proxy=1` 或账号配置 `download_mode=proxy`。

## 不是所有网盘都这样

UA 绑定是**各家 CDN 自己的策略**，115 是实证有此策略的一家。其它网盘（阿里、百度、夸克、天翼……）
要各自实测才知道；判断口径相同：换 UA 取同一条链，看是否被拒。

## 边界

- 本轮只读：未联网核对 Alist 的具体配置项名称，未访问任何外部主机；结论基于"115 签名只绑 UA"这一实测事实
  与各工具的通用架构（直链 vs 中转）。
- 如需 Alist 的具体设置名/版本差异，需要联网查其官方文档（另经授权）。
