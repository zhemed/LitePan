# 排查记录：其它驱动会不会踩 115 同类的直链绑定问题

**结论先行**：这台 LitePan 目前**只能挂 3 种后端：115、天翼云盘、本地目录**（`drivers/all.go` 只注册这三个），
**没有 Alist** —— 全仓 `grep -rln alist` 零命中（Alist 与另外 7 个驱动在早前瘦身时已移除）。
在这三个里，只有 **115** 的直链会把「客户端 UA」带进签名（已修）；天翼的取链**不带**客户端 UA；
本地目录压根不走第三方直链。两跳握手写在 playback 层、**与驱动无关**，将来任何走 302 的驱动都会自动受它保护。

## §1 驱动盘点（R1）

| 驱动 | 是否注册 | 说明 |
|---|---|---|
| `115_Open` | ✓ | 默认 `download_mode=redirect`（302） |
| `189Cloud`（天翼云盘） | ✓ | 默认 302；`proxy` 可切代理 |
| `LocalFs` | ✓ | **强制代理**（`Mode: DownloadProxy` + `ForceProxy: true`，返回 `LocalPath`） |
| `template` | 骨架 | 不是可用驱动 |
| **Alist / OneDrive / 百度 / 夸克 / WebDAV / S3 …** | ✗ | **本仓已删除**（上游有，我们这份精简 fork 没有） |

## §2 逐个驱动的直链性质（R2）

| 驱动 | 302 直链来源 | 客户端 UA 是否进入签名 | 绑定面 | 会不会复现手机那次失败 |
|---|---|---|---|---|
| `115_Open` | 115 CDN（AliyunOSS，带 `k=` 签名） | **是**：`apiCallWithHeaders` 把 `req.UA` 传给取链接口 | **UA**（实测：同 UA 跨 IP 206；换 UA 403） | 会 —— **已由两跳握手修复（v0.0.50，真机已验证）** |
| `189Cloud` | 天翼下载域名（`getFileDownloadUrl.action` 返回的 `fileDownloadUrl`） | **否**：取链走 `apiRequest`（驱动自身的 UA/Cookie）；`resolveUA(req.UA)` 只用于**代理模式**的请求头 | 未知（未见 UA 绑定路径）；注意 302 响应里我们设了 `Referrer-Policy: no-referrer`，若天翼要求 `Referer: cloud.189.cn`，那会是**全平台**失败而不是只在手机 | 大概率不会（无 UA 绑定路径）；**需实测确认** |
| `LocalFs` | 无第三方直链：LitePan 自己读本机文件供流（`LocalPath` + 强制代理） | — | — | 不会 |

## §3 两跳握手的覆盖与边界（R3）

- **覆盖**：握手判定在 `internal/playback/handoff.go`，只看「GET + 非 Inline + 安卓浏览器 UA + `ActionRedirect`」，
  **不认识具体驱动**。所以：任何驱动（含将来新增的 Alist/WebDAV）只要走 302，就自动获得这层保护；
  走代理（`ActionStream`）的驱动/账号根本不经过该分支。
- **改法为什么能覆盖"绑定 UA"这一类**：第二跳是按**系统下载组件自己的 UA** 重新取链，
  所以"取链 UA == 下载 UA"这个前提被强行满足；字节仍由手机直连 CDN，服务器不中转。
- **救不了的两类**（需要在驱动/账号层面处理）：
  1. **直链绑定 IP**：客户端出口 IP 与取链方不同（如手机用流量）→ 302 无论怎么取都过不了；
  2. **直链要求特定 `Referer` 或 Cookie**：浏览器/下载组件带不了我们想让它带的值（我们的 302 还会主动剥离 Referer）。
  这两类的唯一出路是把该账号（或该次下载）切到**代理**：`force_proxy=1`，或账号配置 `download_mode=proxy`。

## §4 关于 Alist 的特别说明（用户点名）

- **现在这台没有 Alist 驱动**，所以"Alist 挂载会不会同样"目前不成立。
- 若将来加回 Alist，要注意**二次签名**这个坑：LitePan 拿到的是 Alist 的 `/d/...?sign=...` 地址，
  而 Alist 自己再向**它背后挂的存储**取直链 —— 如果背后恰好是 115 这种"取链 UA 绑定"的存储，
  签名在 **Alist 请求的那一刻**就用 Alist 的 UA 定死了，浏览器再取必然是 403。
  **我们的两跳握手解决不了这种"套一层"的情况**（第二跳重取的是 Alist 的地址，签名的仍是 Alist 的 UA）。
  处置：让 Alist 侧对该存储走代理，或 LitePan 对该账号走代理。

## §5 新增驱动时的检查清单（R4）

1. `ResolveDownload` 是否把**客户端 UA**（`req.UA`）送进取链请求？（送 → 就可能被绑定，与 115 同类）
2. 返回的 URL 是**第三方 CDN** 还是自家端点？签名参数里是否含 `ua`/`ip`/`d=`（设备）之类字段？
3. 是否依赖 `Referer`？（我们 302 会剥离 Referer）
4. 直链时效多长？（115 是 5 分钟视图；过期失败与 UA 失败的表象相似）
5. 兜底：该驱动/账号能否走 `proxy`？——"IP 绑定"和"必须带 Referer"两类只能靠代理。

## §6 建议的下一步验证（需用户选择）

- **零成本**：在手机上直接试一次**天翼云盘**的文件下载（同一台手机、同一条路径）。
  - 能下 → 天翼无此问题，结案；
  - 不能下 → 我再按需在生产机上做与 115 相同的 UA 对照（会向天翼的下载域名发两次 1 字节请求，需当轮授权）。
- 若确诊天翼也有绑定：优先看它的绑的是 UA 还是 IP，再决定"是否也给该驱动做握手/改默认代理"。
