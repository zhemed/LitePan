# 修复记录：冷却等待后的孤儿任务（0.0.30）

## 现象（用户实测，5000 文件批次）

`bulk5k_0850.bin` 显示「服务器上传 / 等待中 / 账号网络冷却中，30 秒后自动重试」，
**35 秒后无任何变化**（updated_at 停在 20:21:16）；整批 4383 暂停 + 616 成功 + 0 失败。

## 根因（0.0.24 引入）

`internal/upload/worker.go` 冷却分支把任务置回 `pending` 后直接 `return`：

```go
m.patch(... st.Status = StatusPending ...)   // 任务"看起来"已重新排队
select { case <-ctx.Done(): case <-time.After(wait): }
return                                        // ← runTask 协程随之退出
```

pending 任务的执行依赖**各自在 `acquireRunSlot` 等待的协程**；协程退出后没有任何
机制重新接管该任务 → 永久滞留（提示语承诺的"自动重试"从未发生）。

**附带竞态**：冷却分支无条件把状态写成 pending，可能覆盖同一时刻用户发起的暂停。

## 修复

| 改动 | 说明 |
|---|---|
| `runTask` 循环重入 | `executeUpload` 返回 `requeue=true` 时释放槽位后重新 `acquireRunSlot` 再执行；`acquireRunSlot` 已有"状态非 pending 即退出"校验，对暂停/取消/删除天然安全 |
| `executeUpload` 返回 `requeue bool` | 冷却分支在等待结束后返回 `m.canCooldownWait(taskID)` |
| 新增 `canCooldownWait` | 仅当任务仍可重试（非暂停/取消/停止）才置 pending；等待期间被暂停/取消 → 保持其状态且不重入 |

## 验证

| 项 | 结果 |
|---|---|
| 单测（3 组新增） | 冷却结束 `requeue=true` 且回 pending + 提示 + 置顶 ✓；暂停态不被覆盖且不重入 ✓；取消/停止态拒绝冷却等待 ✓ |
| 既有套件 | `go vet` 全绿、`go test ./...` 零失败、`check:memo` 16 断言全过 |
| **部署后实测** | 卡住的孤儿任务 `bulk5k_0850.bin` 在 0.0.30 启动后被接管并**上传成功** ✓（重启恢复路径对 pending 任务重新挂起协程） |
| 批次现状 | 4383 暂停 + 617 成功 = 5000（用户暂停中，无异常、无失败） |
| 发布 | 0.0.30 三 tag（digest `c8aae4f9`）+ release + 部署三连 |

## 用户侧说明

- 「账号网络冷却中，30 秒后自动重试」本身是**正常保护**（0.0.24 起：账号连续 3 次网络失败 → 30 秒冷却，避免整批秒级判死）
- 0.0.30 起该提示会**真的**在 30 秒后自动重试；此前会卡住不动
- 若再遇到卡住的任务：暂停→继续即可手动恢复（重启恢复也会接管）
